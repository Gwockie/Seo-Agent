## Parallel work and integration

Development and SEO interpretation can run together because the builder uses
synthetic data and the SEO task owns the only live workspace. Both inspect current
main; neither merges stale whole branches or overwrites the other's source work.
Do not edit overlapping files, access another client's evidence or copy ignored
credentials/workspaces. Messages to other chats need human authorization.

Only the primary checkout collects live evidence. Its current lock is scoped to
the checkout, so two worktrees cannot safely collect against the same workspace
by assuming their locks coordinate. Scheduling must address this explicitly.
Collection, page checks, import, backup and migrations are coordinated operations.

Merge tested public changes sequentially. The builder can complete and merge its
code while SEO proposals are prepared, but primary restart/migration/activation
requires idle verification and protected rollback evidence. Keep a built live
schedule disabled until the SEO task releases the primary workspace and the
reviewed schedule is enabled by the user. Then perform bounded live validation
from the canonical primary installation, never a disposable worktree.

SEO recommendations remain useful without weekly scheduling. Public website
changes still require exact-action human approval; this Git/source authorization
does not approve website publication or host/OAuth/security changes. See the
[website policy](website-change-policy.md).
